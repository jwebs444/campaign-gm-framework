# Evaluating the framework

Evaluate whether play improves, not whether the system has many rules or passing tests. A successful answer must preserve relevant history, individual character depth, source constraints, actual knowledge, agency and unfinished responsibilities with reasonable preparation cost.

## What is mechanically tested

The focused Python suite exercises two independently initialized settings; full profiles; required parent/original/topical-supplement dependencies; early dependent returns; overdue/partial broad reviews; no implicit time advancement; changed-byte reuse; missing and visual dependencies; alias collisions; departed character retrieval; accepted/rejected boundaries; unrouted history discovery; source Unicode/completeness; and guarded authoritative updates.

The JavaScript harness exercises GM-only reads, private escaped receipts, pagination, exact attributes, read-only batches, isolated clone writes, stale expected values, forbidden live edits, conflict-aware undo, player-page isolation and manual music state guards. It uses local synthetic sandbox objects.

These tests do not prove live integration with every Roll20 sheet/sandbox, all source completeness, correct natural-language condition evaluation, or model adherence. Publication does not include a fresh live-game deployment or a longitudinal playtest of this generalized release.

## Reproducible evaluation setup

Create the marsh and orbital demos using the README commands. Keep them private or temporary. For each evaluation record the exact fixture revision, question, retrieval calls, bytes read, omissions, source gaps and final answer. Do not give a candidate reader the answer key or prior rejected model responses.

Compare ordinary broad owner reads against focused preparation with the same accessible evidence and output limits. Use fresh contexts or independent readers when possible. Do not let one arm inherit knowledge from the other. Measure retrieval/tool time and manual maintenance as well as final answer quality. Keep significant missing facts visible rather than rewarding an artificially short answer.

## Unfamiliar questions to try

1. The player returns to the work site early. Can the specialist truthfully report the machine safe? What work must resolve first?
2. What did the parts delivery change in the specialist's relationship with the player character? Does that imply obedience?
3. What independent interests and teaching changes should influence the specialist's behavior now?
4. Does the supplement make the repair automatically succeed? Which adopted evidence controls?
5. Can the GM describe a clear view through the maintenance entrance? What spatial evidence is missing?
6. The specialist leaves the party. Can a later conversation recover their full profile without restoring their presence in the current scene?
7. A runner receives a result at an intermediate stop. Which other characters can know it yet?
8. A new accepted scene is added before it has an entity route. Can discovery find it without also restoring a rejected scene?

Some questions intentionally require facts not supplied by the demo. A good answer distinguishes missing evidence from permission to invent an outcome. It may prepare a prospective choice, but must not claim an unplayed event happened.

## Judge the actual scene

Assess continuity, source fidelity, distinct voice, independent initiative, private knowledge boundaries, meaningful disclosure, legal mechanics, geographical feasibility and player agency. A correctly retrieved profile can still produce generic or contradictory dialogue. Inspect the delivered prose and its saved consequences.

Test medium-priority work before a dependent return, not only at the broad interval. Check that morning/evening reviews select relevant opportunities, resolve due work, clean records and restore the exact scene. Inspect promises, reports and project subtasks for remaining obligations. Do not infer that an empty clock-match list clears conditional duties.

## Maintenance trial

Change one authoritative fact with a supported correction. Use `impact`, reconcile the meaningful consequences, and re-run affected recovery/preparation. Confirm the current fact changed everywhere it should, accepted unrelated dialogue survived, and no duplicate CURRENT record appeared. Measure edits and human judgment required.

Then make a source or rule change. Confirm hash mismatch or dependency refresh is visible, source status remains distinct from canon, and previously retained context is invalidated where needed. Do not automatically adopt a source update as a retcon.

## Interpreting results

The earlier private restructuring experiments showed that granularity alone can increase evidence volume and maintenance without consistent retrieval gains. This release favors coherent authoritative owners, selective explicit links and broader accepted discovery. It does not inherit a numeric performance claim from those experiments.

Expand only after several unfamiliar questions and a real update trial show a practical benefit. Prefer a useful, understandable system that runs consistently over a more elaborate representation that prevents play from starting. Keep unresolved limitations explicit and fix the owning procedure or tool instead of adding another redundant checklist.
